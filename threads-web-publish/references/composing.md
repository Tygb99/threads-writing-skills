`threads-web-publish` 상세 참조. 본문·자답글을 입력하고 사진과 alt를 붙일 때 읽는다.

## 1. 본문 입력 — 인라인 Enter는 즉시 게시다

가장 비싼 함정부터. **인라인 답글창에서 Enter는 줄바꿈이 아니라 발행이다.** 줄바꿈이 섞인 문자열을 그대로 타이핑하면 첫 줄만 올라가고 나머지는 사라진다.

- 여러 줄은 **확장(⤢) 창이나 수정 창**에서 쓴다. 거기서는 Enter가 줄바꿈으로 동작한다.
- 인라인 창을 꼭 써야 하면 줄바꿈을 `Shift+Enter`로 넣는다.

**여러 줄을 넣을 때는 브라우저 도구의 `type` 액션으로 줄바꿈을 포함해 통째로 입력한다.** 모달 작성창에서는 Enter가 줄바꿈이라 이게 가장 확실하다.

`execCommand`로는 줄바꿈이 들어가지 않는다 — 2026-07-27 실측:

- `document.execCommand('insertText', false, '...\n...')` → **`\n`이 통째로 무시되고 한 문단으로 뭉친다.** 글자는 다 들어가는데 줄 구조만 사라져서, 확인 없이 게시하면 문단 없는 벽 글이 올라간다.
- `document.execCommand('insertLineBreak')`를 줄 사이에 끼워도 → 역시 줄바꿈이 안 생기고, 커서가 튀어 문장 순서까지 뒤섞였다.

한 줄짜리 텍스트를 넣거나, 이미 있는 오타를 Range 선택 후 바꿔치기할 때는 `insertText`가 여전히 가장 안전하다(Lexical 에디터라 DOM 직접 주입은 저장 시점에 날아간다). 즉 **줄바꿈이 없으면 `insertText`, 있으면 `type`**.

작성창을 먼저 클릭해 포커스를 준다. 그리고 **클릭 직후 바로 타이핑하면 앞 글자가 잘린다** — `같은 `이 통째로 날아간 적이 있고, 2026-07-29에도 본문 첫 줄 `사용량이 `가 그대로 유실됐다.

이건 가끔이 아니라 **거의 매번**이다. 그래서 방어를 절차에 박아둔다:

> **모든 편집 칸은 `.`으로 시작해서 타이핑하고, 입력이 끝나면 맨 앞 1글자를 지운다.**

```javascript
// 맨 앞 한 글자 제거
const el = document.querySelectorAll('div[role="dialog"] div[contenteditable="true"]')[i];
el.focus();
const first = document.createTreeWalker(el, NodeFilter.SHOW_TEXT).nextNode();
const r = document.createRange(); r.setStart(first,0); r.setEnd(first,1);
const s = getSelection(); s.removeAllRanges(); s.addRange(r);
document.execCommand('delete');
```

잘림이 나도 잃는 건 `.` 하나다. 지우기 전후로 `innerText` 앞부분을 찍어 확인한다.

### ⚠️ 가드 절차는 글자 수 검증을 무력화한다 (2026-08-01, Aside repl)

가드 `.`을 지우는 절차에는 함정이 하나 붙어 있다. **타이핑 중 글자가 유실되면 가드를 지운 것이 그 손실을 상쇄해 글자 수가 맞아떨어진다.**

실제로 겪은 것: 본문을 타이핑하고 가드를 지운 뒤 218자가 초안과 정확히 일치해 검증을 통과시켰다. 그런데 예약 저장 후 다시 열어보니 `코드가 /opt/.manus`가 **`드가 /opt/.manus`**로 저장돼 있었다. 중간에서 `코` 한 글자가 날아갔고, 앞에서 `.` 한 글자를 지운 것이 정확히 -1 +1로 맞춰준 것이다.

즉 **글자 수 일치는 무결성 증명이 아니다.** 가드를 쓰는 이상 이 상쇄는 구조적으로 일어날 수 있다. 검증은 초안 문자열과 `innerText`를 **문자 단위로 비교**한다:

```javascript
const got = el.innerText.replace(/\s+$/, "");
const exp = draft.replace(/\s+$/, "");
if (got !== exp) {
  for (let k = 0; k < Math.max(got.length, exp.length); k++) {
    if (got[k] !== exp[k]) {
      console.log("first diff at", k, JSON.stringify(got.slice(k-10, k+10)), "vs", JSON.stringify(exp.slice(k-10, k+10)));
      break;
    }
  }
}
```

고치는 것은 캐럿을 손실 지점 앞에 Range로 두고 빠진 글자만 타이핑하면 된다. 예약 배너가 붙은 편집 모드에서도 먹히고 이미지와 alt는 유지된다(실측: alt 67자·384자, 이미지 2장 보존). 마지막에 `업데이트`를 눌러야 반영된다.

```javascript
const w = document.createTreeWalker(el, NodeFilter.SHOW_TEXT);
let n;
while ((n = w.nextNode())) {
  const i = n.textContent.indexOf("드가 /opt/.manus");   // 손실된 뒤의 문자열
  if (i !== -1) {
    const r = document.createRange(); r.setStart(n, i); r.setEnd(n, i);
    const s = getSelection(); s.removeAllRanges(); s.addRange(r);
    break;
  }
}
// 이 상태에서 빠진 글자만 타이핑한다
```

한글은 **리터럴로 넘긴다.** 도구 인자에 `\uXXXX` 이스케이프로 넘기면 코드포인트를 틀려 오타가 난다(블로그→바로그, 간격→간겁). 게시 전에 전문을 검증하고, 오타는 TreeWalker로 텍스트 노드를 찾아 Range 선택 후 `insertText`로 교체한다.

### 해시태그 — 공백이 경계를 만든다

해시태그를 치면 주제 태그 자동완성 팝업이 뜬다. 전체 문자열을 하나의 태그로 만들려 한다.

**`Escape`로 팝업을 닫아도 토큰 경계는 안 생긴다.** 2026-07-29 실측: `#코덱스` → Escape → `#장애인` → Escape … 순으로 넣었더니 저장 시점에 **`#장애인접근성디버깅바이브코딩` 한 덩어리로 병합**됐다. 화면에는 태그처럼 보여서 눈으로는 안 걸리고, `innerText` 검증에서만 잡힌다.

경계를 만드는 것은 Escape가 아니라 **뒤따르는 공백**이다:

> **`#태그 ` 단위로, 뒤 공백까지 붙여 하나씩 넣는다.** 매 태그 후 `innerText` 마지막 줄을 확인한다.

이미 뭉친 토큰은 부분 교체가 덧붙는 식으로 깨지므로(`#장에인#장애인`), 캐럿을 뒤에 놓고 글자 수만큼 `BackSpace`로 지운 뒤 다시 넣는다.

### Escape는 작성창까지 닫는다

**팝업만 닫으려고 누른 `Escape`가 작성창을 닫는다.** 2026-07-29에 이걸로 `임시 저장하시겠어요?` 확인창이 떴다.

- **팝업은 X 버튼으로 닫는다.** Escape에 의존하지 않는다.
- 확인창이 뜨면 **작업을 이어갈 때는 `취소`**다. `저장 안 함`은 되돌릴 수 없다.
- 확인창이 2개 겹쳐 뜨는 경우가 있다. 하나 닫고 스크린샷으로 재확인한다.

임시 저장은 잘 버틴다 — 창이 닫혀도 본문·줄바꿈은 임시 저장본에 남았다. 다만 **뭉친 해시태그는 뭉친 채로 저장된다.** 저장이 내용을 고쳐주지는 않는다.

`Cmd+A`는 편집 영역 안을 클릭한 뒤에 눌러야 한다. 사진이나 여백을 클릭한 상태면 페이지 전체가 선택된다.

### 내용 검증

```javascript
const e = document.querySelectorAll('div[contenteditable="true"]');
const n = s => s.replace(/\n/g,'').replace(/ /g,' ').trim().length;
Array.from(e).map((el,i) => `${i+1}=${n(el.innerText)}자`).join(' / ')
```

글자 수는 **줄바꿈 제외**로 센다. 줄바꿈을 늘려도 길이 계산에 영향이 없다.

## 2. 자답글은 `스레드에 추가`로 묶는다

여러 편으로 나눌 글은 확장 창의 **`스레드에 추가`** 버튼으로 칸을 늘려 한 번에 게시한다. 따로따로 올리면 체인이 아니라 형제 답글로 흩어져 순서가 뒤섞인다.

한 번에 게시되므로 "자답글을 본문 직후에 올린다"는 조건도 자동으로 충족된다. 3일 늦게 단 자답글은 조회가 거의 안 붙는다.

**칸이 늘어나면 버튼이 화면 밖으로 밀린다** (2026-08-01, Aside repl). 자답글을 하나 채운 뒤 `스레드에 추가`를 다시 누르려면 작성창 안에서 스크롤해야 한다. DOM 좌표는 `visible: true`로 나오는데 실제로는 뷰포트 밖이라, 클릭해도 칸 수가 늘지 않고 조용히 무시된다. 클릭 후 `contenteditable` 개수가 실제로 늘었는지로 판정한다.

```javascript
await page.mouse.move(820, 700);
await page.mouse.wheel(0, 700);   // 작성창 안에서 스크롤
// 그 다음 버튼 좌표를 다시 조회해 클릭
```

### 밀려난 버튼을 그냥 누르면 작성창이 닫힌다 (2026-08-15, claude-in-chrome)

위 항목은 "클릭이 조용히 무시된다"고만 적혀 있었는데, **더 나쁜 결과가 있다.** 버튼이 작성창 아래로 밀린 상태에서 그 좌표를 누르면 클릭이 **작성창 바깥(오버레이)에 떨어져 `임시 저장하시겠어요?` 확인창이 뜬다.** 여기서 `저장 안 함`을 누르면 그때까지 쓴 본문이 통째로 날아간다.

실제로 본문 191자를 다 쓰고 `스레드에 추가`를 누르려다 이걸 맞았다. `취소`를 눌러 원문을 지켰다.

- `getBoundingClientRect().y`가 뷰포트 높이에 가깝거나 넘으면(예: 810 / 843) **누르지 말고 먼저 스크롤한다.**
- 스크롤 후 **스크린샷으로 버튼이 작성창 안쪽에 있는지 눈으로 확인**하고 누른다. 좌표만 믿지 않는다.
- 이미 확인창이 떴다면 **`취소`**다. 절대 규칙 4번과 같다 — `저장 안 함`은 되돌릴 수 없다.

### 칸을 클릭한 뒤 `activeElement`로 포커스를 확인하고 타이핑한다 (2026-08-15, claude-in-chrome)

칸이 늘어나거나 별도 패널(예: `대체 텍스트 추가`)이 뜨면 **DOM 좌표가 밀려 클릭이 빗나가고, 그 상태로 타이핑하면 글자가 어디에도 안 들어간다.** 실제로 alt 214자를 두 번 통째로 날렸다 — 입력란은 비어 있고 오류도 없다.

타이핑 전에 한 줄로 확인한다. 이게 있으면 유실 자체가 안 일어난다.

```javascript
const els = [...document.querySelectorAll('div[role="dialog"] div[contenteditable="true"]')];
els.indexOf(document.activeElement)     // 넣으려는 칸의 인덱스와 같아야 한다. -1이면 포커스가 없다
```

## 3. 사진 첨부 — 클립보드가 유일한 경로

에이전트가 파일 업로드 도구로 직접 올리는 건 거부된다(세션에 공유된 파일만 허용). 프로젝트 폴더도, 스크래치패드도 안 된다. macOS에서는 클립보드로 우회한다:

```bash
osascript -e 'set the clipboard to (read (POSIX file "/절대/경로/파일.png") as «class PNGf»)'
```

그 뒤 작성창 텍스트 영역을 클릭하고 `Cmd+V`.

- **webp는 Threads가 안 받는다.** `sips -s format png 원본.webp --out 결과.png`로 변환한다.
- 폰 스크린샷은 맥에 파일이 없다. 메신저로 옮기면 확장자가 `.webp`로 오는 경우가 많다.

### 사진(실사)은 JPEG로 줄여서 붙인다 (2026-08-07, claude-in-chrome)

클립보드는 PNG만 받는 게 아니다. **JPEG도 된다:**

```bash
osascript -e 'set the clipboard to (read (POSIX file "/절대/경로/사진.jpg") as JPEG picture)'
```

이걸로 사진 3장을 붙여 예약까지 정상 발행 확인했다(2026-08-07 전동휠체어 사고 글).

쓰는 이유는 용량이다. **실사 사진을 PNG로 바꾸면 용량이 몇 배로 뛴다** — 같은 3장이 PNG 1500×2000에서 합계 14.4MB(1200×1600으로 줄여도 9.7MB)인데, JPEG 1500×2000 품질 88은 **합계 2.5MB**였다. 업로드 실패 사례(합계 12.2MB, §3 위)를 PNG 사진으로는 몇 장 만에 다시 밟는다.

- 실사 사진: **JPEG 유지, 긴 변 2000px 이내, 품질 85~90.**
- 스크린샷·글자/선 그래픽: PNG 유지(잘 압축되고 글자가 또렷하다).
- EXIF orientation은 픽셀에 굽고 저장한다. PIL은 저장 시 EXIF를 안 쓰므로 이중 회전(§3 아래)이 안 생긴다:

```python
from PIL import Image, ImageOps
im = ImageOps.exif_transpose(Image.open(src))   # 회전을 픽셀에 반영
im.thumbnail((1500, 2000))                       # 긴 변 2000px 이내
im.save(dst, "JPEG", quality=88)
```

### 게시가 통째로 실패할 때 — `게시물을 업로드하지 못했습니다` (2026-08-01, claude-in-chrome)

`게시`를 누르면 `게시 중...`이 떴다가 **`게시물을 업로드하지 못했습니다`** 토스트로 끝나고 작성창이 닫히는 경우가 있다. 실제로 겪은 조건은 사진 2장 합계 약 12.2MB(1672×2090 PNG 2.3MB + 3200×4000 PNG 9.9MB)였고, 같은 문안 그대로 **1600×2000으로 줄여 1.9MB + 2.6MB로 다시 붙이니 한 번에 올라갔다.**

⚠️ **용량이 원인이라고 확정하지 않았다(미검증).** 대조 실험을 하지 않았고, 재시도 사이에 사진 외에 자답글 텍스트를 다시 쓴 변경도 함께 들어갔다. 임계값도 모른다. 다만 첨부를 가볍게 만드는 것이 값싼 첫 시도라, 실패하면 먼저 줄여 본다. 원본 화질이 필요한 것이 아니면 **긴 변 2000px 안쪽**으로 두면 이 사례의 조건은 피한다.

토스트의 **`보기`를 누르면 작성창이 초안 그대로 복원된다** — 본문·자답글·사진·alt가 남아 있어 처음부터 다시 쓸 필요는 없다. (2026-08-01 실측. 이때 자답글에 섞여 있던 `.` 한 줄과 여분의 줄바꿈은 복원 과정이 만든 것이 아니라 사용자가 직접 넣은 것이었다 — 복원이 텍스트를 바꾼다는 근거는 없다.)

### EXIF orientation은 두 번 먹는다 (2026-08-01, 로컬 도구)

폰 사진은 픽셀이 눕고 EXIF `orientation`으로 세우는 경우가 많다. 여기서 회전 도구를 잘못 쓰면 **브라우저가 한 번 더 돌려서** 눕힌 채로 첨부된다.

- `sips -r 90`은 픽셀만 돌리고 **orientation 태그는 그대로 남긴다.**
- `ffmpeg`는 그 태그를 PNG로 복사한다. `sips -g pixelWidth`는 태그를 반영한 값을 보여줘 파일이 멀쩡해 보이는데, Chrome은 태그를 한 번 더 적용해 가로로 붙인다.
- 붙인 뒤 `naturalWidth x naturalHeight`가 의도와 뒤바뀌어 있으면 이걸 의심한다.

```python
from PIL import Image, ImageOps
im = ImageOps.exif_transpose(Image.open(src))   # EXIF를 픽셀에 반영
im.save(dst, "PNG")                              # PIL은 EXIF를 쓰지 않는다
```

## 4. 다중 이미지는 세로 타일로 센터 크롭된다

사진이 2장 이상이면 캐러셀로 묶이며 **세로 타일 기준으로 잘린다.**

- **가로로 납작한 이미지(예: 472×54 메뉴바 크롭)는 쓰지 말 것.** 핵심 숫자가 전부 잘리고 가운데 파편만 확대된다.
- 비교용 2장은 **비슷한 세로 비율끼리** 묶어야 둘 다 읽힌다(786×1204 + 802×1252 조합은 정상).
- 납작한 이미지를 꼭 써야 하면 단독 1장으로 올리거나 정사각형으로 패딩한다.
- **비율이 다른 2장을 꼭 같이 올려야 하면 둘 다 같은 비율로 패딩한다** (2026-08-01, claude-in-chrome). 가로 포스터(1.78:1)와 세로 사진을 그대로 넣으면 양쪽 다 잘린다. 검은 여백으로 **둘 다 4:5**로 맞춰 붙이니 잘리는 부분 없이 전체가 보였다. `ffmpeg -vf "pad=..."`나 PIL로 캔버스를 만들어 가운데 붙이면 된다.

## 5. alt 텍스트

사진 위에 마우스를 올리면 좌하단에 `···`이 뜬다 → **`대체 텍스트 추가`** → 입력 → `완료`.

**`···`가 화면 밖에 있으면 hover로도 안 나온다.** 세로로 긴 이미지는 작성창을 스크롤해 이미지 하단이 보이게 한 뒤 hover해야 한다. 안 보이면 스크롤부터 의심한다.

- 사진이 여러 장이면 **각 사진마다 따로** 넣는다.
- **길이 제한은 넉넉하다** — 581자가 잘림 없이 들어갔다(2026-07-29). 줄바꿈 없는 한 문단이므로 `insertText`로 통째로 넣으면 된다.
- alt 입력란도 `contenteditable`이라 본문 칸과 같이 잡힌다. **인덱스를 확인하고 쓸 것** — 본문 칸에 alt를 쓰는 사고가 난다.
- 예약 저장 후 다시 열면 이미지 `src`가 `blob:`에서 `https://scontent-...`로 바뀐다. **`blob:`만 세는 검증 스크립트는 0을 반환한다** — 첨부가 사라진 게 아니다.
- **`대체 텍스트 추가` 메뉴 항목이 DOM 조회로 안 잡히는 경우가 있다** (2026-08-01, Aside repl). `···`를 눌러 메뉴가 열리고 스크린샷에도 항목이 보이는데, `div[role="button"]`에서 텍스트로 찾으면 `null`이 나왔다. 이때는 스크린샷으로 항목 위치를 읽어 **화면 좌표로 클릭**한다. 좌표를 잘못 잡으면 메뉴가 닫히기만 하므로, 클릭 후 `aria-placeholder`가 `시각적으로`로 시작하는 `contenteditable`이 생겼는지로 성공을 판정한다.
- **alt를 저장해도 메뉴 항목은 계속 `대체 텍스트 추가`다** (2026-08-01, claude-in-chrome). `수정`으로 바뀌지 않고 이미지 위 배지도 눈에 잘 안 띄어서, 라벨만 보면 저장이 안 된 줄 안다. 저장 여부는 **항목을 다시 열어 입력란의 `innerText`를 확인**해 판정한다. 발행 뒤에는 피드의 `img.alt` 길이로 최종 확인할 수 있다.
- alt 입력란에도 **가드 `.`을 쓴다** (2026-08-01, Aside repl). 본문과 같은 앞 글자 잘림이 일어난다. 384자 alt가 잘림 없이 저장됐고, 지운 뒤 초안 문자열과 일치하는지 대조했다.
- **alt가 통째로 유실되는 사례가 있다** (2026-08-12, claude-in-chrome). 첫 시도 입력이 저장 후 확인하니 전부 사라져 있었다. **가드를 2개(`..`)로 늘리고**, 입력 후 반드시 입력란을 다시 열어 초안 문자열과 문자 단위로 대조한다 — 대조 없이는 유실을 알 수 없다.
  - **원인을 2026-08-15에 잡았다: 포커스다.** `대체 텍스트 추가`는 별도 패널로 떠서 페이지가 스크롤되고, 그 전에 잡아둔 좌표를 누르면 입력란을 빗나간다. 그 상태로 타이핑하면 글자가 어디에도 안 들어가고 오류도 없다(같은 날 214자를 두 번 날렸다). **클릭 후 `activeElement`의 `aria-placeholder`가 `시각적으로`로 시작하는지 확인하고 타이핑한다** — §2 끝의 포커스 확인 항목과 같다. 확인만 넣으면 유실이 안 일어나므로 사후 대조보다 이쪽이 먼저다.
- **가드 제거 시 `cmd+Left`를 쓰지 말 것** (2026-08-12). `cmd+Left`는 문서 처음이 아니라 **시각적 줄의 처음**으로 간다 — 긴 텍스트가 줄바꿈돼 있으면 엉뚱한 위치의 글자를 지운다. 문서 처음으로 가는 것은 `cmd+Up` 계열만 믿는다.

```javascript
Array.from(document.querySelectorAll('div[role="dialog"] img'))
  .filter(i => i.width > 100)
  .map(i => `${i.width}x${i.height} alt=${(i.alt||'').length}자`)
```

## 6. 작성창 조작 함정 (2026-07-31, Aside repl)

브라우저 자동화로 작성창을 다룰 때 반복해서 값을 치른 것들이다.

**캐럿은 클릭으로 끝에 가지 않는다.** 칸을 클릭하거나 `Meta+ArrowDown`을 눌러도 캐럿이 직전 편집 위치(문단 중간)로 가는 일이 반복돼 URL이 글 중간에 박혔다. 확실한 방법은 Range로 끝으로 보내는 것이다:

```javascript
const r = document.createRange();
r.selectNodeContents(el);
r.collapse(false);              // 끝으로
const s = getSelection(); s.removeAllRanges(); s.addRange(r);
```

**`cmd+Left`는 문서 처음이 아니라 시각적 줄 처음으로 간다** (2026-08-12). 앞쪽 가드를 지우러 갈 때 `cmd+Left`를 쓰면 줄바꿈된 긴 문단에서는 현재 줄의 시작으로만 이동해 엉뚱한 글자를 지운다. 문서 처음 이동은 `cmd+Up`(또는 `Meta+ArrowUp`) 계열만 쓴다.

**본문 칸이 snapshot에 안 잡히면 스크롤을 의심한다.** 작성창을 열면 스크롤이 아래쪽에 있어 본문 칸이 트리에 안 나오는 경우가 있다. 스크롤 컨테이너(`generic [scrollable]`)의 `scrollTop = 0`으로 올린 뒤 다시 snapshot을 찍으면 모든 칸 ref가 나온다.

**해시태그를 넣으려고 다시 클릭하지 않는다.** 본문 입력 후 재클릭하면 캐럿이 중간으로 튀어 문장 사이에 태그가 박힌다. 본문과 해시태그는 한 번의 `type`으로 이어서 넣는다.

**DOM 직접 삭제는 쓰지 않는다.** `execCommand('delete')` + TreeWalker/Range 조합은 Lexical 에디터에서 줄 순서를 뒤섞을 수 있다. 링크는 텍스트 노드로 잡히지 않아 TreeWalker 검색 자체가 실패한다. 칸을 비우고 다시 타이핑하는 편이 확실하다.

### Aside repl로 조작할 때

- `attachBrowserTab`이 `No open browser tab found`로 실패한 이력이 있다. `openTab()`으로 새 탭을 여는 편이 확실했다.
- `page.evaluate`가 잘못된 프레임을 잡아 `document.querySelectorAll('div[role="dialog"]')`가 0을 반환한 일이 있다. **ref 기반 조작과 `locator.evaluate`를 우선한다.**
- 확장 작성창은 `role="dialog"`가 아니라 **`role="menu"`**로 잡힌다(2026-07-31 확인). `dialog`로만 찾으면 작성창을 못 찾는다. 확인창은 `dialog`다.
- 액션마다 ref가 무효화되니 새 snapshot을 찍는다. `page.waitForTimeout`은 없고 `sleep(ms)`를 쓴다. REPL 스코프가 유지되므로 변수명을 매번 새로 쓴다.
- **게시 직후 `document.body.innerText` 검색이 렌더링 지연으로 방금 올린 내용을 못 찾는 일이 자주 있다.** 스크린샷이나 snapshot으로 재확인한다. 텍스트 검색 실패를 "게시 안 됨"으로 오판하지 않는다.
- 좌표 클릭은 스크린샷 좌표와 뷰포트 좌표가 달라(실측 배율 약 0.71/0.72) 엉뚱한 링크를 눌러 페이지가 이동하는 사고가 났다. 가능하면 ref 클릭을 쓴다.
